# Visual Writing system

Writing is the canonical collection of interactive technical stories. Work explains what Hafiz built; Writing explains how he investigates and learns. Notes remain lightweight. Published story URLs are `/writing/<slug>/`; existing Blog and Visual redirects remain available.

## Architecture

| Layer | Location | Responsibility |
| --- | --- | --- |
| Publication metadata and prose | `src/content/writing/*.mdx` | Title, summary, dates, category, tags, author, sources, related Work, publication status, chapter order, short narrative and technical details |
| Storyboard | `src/data/writing/stories.json` | Opening tension, chapter labels/captions, full-width chapter flags, reflection and preview scene |
| Evidence | `src/data/writing/*.json` | Small derived observations, source pins, units and known limits; no model training at runtime |
| Custom scenes | `src/visual/writing/*.ts` | Subject-specific geometry, annotations and state transitions |
| Registry | `src/visual/writing/registry.ts` | Build-time renderer registration; unknown scene IDs and metadata/order mismatches fail the build |
| Layout and components | `src/components/writing/`, `src/layouts/VisualWritingLayout.astro` | Opening, controls, progress, sticky stage, native narrative, inline fallback, sources and reflection |
| Scroll lifecycle | `src/scripts/writing/controller.ts` | Native passive scroll, one scheduled animation frame, active chapter, progress, responsive/reduced-motion mode and cleanup |
| Client scene adapter | `src/scripts/writing/scene-viewer.ts` | Move persistent SVG marks and fade chapter annotations; never replace the canvas |

Recruitment retains its approved renderer, CSS, opening and ending in `RecruitmentLayout.astro`. Its controller uses the same lifecycle and its chapter/stage components wrap the shared components with the original class names. This is a compatibility adapter, not a second scroll engine. Its profile data remains under `src/data/scrolly/`; specialized rendering remains under `src/visual/recruitment/`.

The registry is imported at build time. An article sends only its own mark states and chapter metadata to the browser. Other articles' datasets do not enter that reader's client bundle. The homepage and Writing index use the same content collection and `WritingRow` component; preview SVGs are generated by the same scene renderers at build time.

## Available building blocks

- `VisualArticleLayout`: site shell, Reading depth controls, two chapter navigation surfaces, stage/narrative/ending slots.
- `StoryHero`, `StoryProgress`, `StoryStage`, `StoryStep`, `ArticleStep`, `StoryEnding`, `SourceNote`, `TechnicalDetail`.
- `composeScene` / `markMarkup`: persistent identified marks and annotation layers, with a single-state inline alternative.
- SVG primitives: escaped text, line, dot, bar, categorical bars, timeline, line path with explicit discontinuities, accessible SVG wrapper.

The pitch, thermal grid, confusion matrix, forecasting loop and team/service contract are custom scenes. They are intentionally not forced into one generic diagram component. Add a reusable primitive only when another real scene needs it.

## Narrative and motion

Each `Step` asks or answers one question using short paragraphs. `Technical` contains derivation, code settings, source caveats or deeper interpretation. Story mode keeps these native disclosures available; Technical opens them together. Without JavaScript each disclosure still works.

`mountStory` calls `enter(id)`, optional `leave(id)`, optional `progress(id, fraction)`, and optional `mode(enhanced, reduced)`. Scenes own visual state. They must not control page scrolling. Marks keep stable IDs across chapters; transforms interpolate their positions. Opacity changes remove irrelevant marks and introduce explanatory annotations. Full-width chapters use the same canvas while the prose moves above it; expanded technical notes reserve more space dynamically.

At widths above 900 pixels with motion permitted, the narrative controls one sticky stage. At tablet and phone sizes every chapter has a locally placed visual. Reduced motion and JavaScript-free reading show every static chapter visualization, with all prose, captions and sources. No scroll interception, wheel handler or animation framework is required. Respect the system's reduced-motion preference even though the site has no manual motion button.

## Create an article

1. Define the question, intended audience, main tension and a 4–8 chapter storyboard. For each chapter record what the reader learns, what moves or appears, and what evidence supports it.
2. Run `npm run new:story -- my-investigation`. It creates draft MDX, a renderer, a storyboard entry and registration. The starter is illustrative and is excluded from published routes, previews and search until both `draft: false` and `status: Published` are set.
3. Edit the frontmatter once. Fill `title`, `summary`, `date`, optional `updated`, `category`, `tags`, `authors`, `cover`, `work` and `sources`. Optional `project` supports repository/demo/paper URLs. Set `story.id`, `story.estimatedReadTime` and the ordered `story.chapters` to match the renderer's storyboard exactly.
4. Replace the starter text in each `<Step story="my-investigation" id="…">`. Put advanced detail in `<Technical title="…">`. Keep source links in frontmatter; the closing source list reads from it.
5. Add a small JSON evidence export under `src/data/writing/`. Record source/version/hash, units, selection rules and absent evidence. Never disguise conceptual marks as measured data.
6. Design the article's renderer. Return a `MarkState[]` with stable IDs from `state(id, mobile)`; render geometry with `composeScene`, custom SVG and the small primitives. The scaffold registers these functions automatically. Select the representative `preview` scene in its storyboard. Use `wide: true` on a middle chapter when a comparison benefits from the full viewport.
7. Check every chapter with Story and Technical depth, both themes, desktop, tablet and phone. Read it without enhancement. Verify labels, geometry, source boundaries and the final reflection. Do not publish the generic starter illustration.
8. Set publication flags, run `npm run format`, `npm run build`, `npm run check`, `npm test`, `npm run check:links`, and `npm run lint`. Confirm the article and its SVG preview appear on Writing and any category archive. The build validates registered IDs/order; changing metadata alone cannot silently select the wrong scene.
9. Review the static package, then publish through GitHub Pages when authorized. The existing `.github/workflows/deploy.yml` builds the site and deploys `dist` on pushes to `main` or manual dispatch. Verify the live website after deployment; a successful workflow alone is not a complete release check.

Templates: `templates/visual-story/article.mdx.template`, `scene.ts.template`, `story.json`. The scaffold refuses existing files and reserved category slugs. For manual authoring, copy these files and register the renderer explicitly.

## Evidence boundaries

Recruitment's frozen V1 remains unchanged. Source reproducibility does not establish scouting, expert or predictive validity. Do not upgrade its validation claims.

Thermal's image counts and reported accuracies come from the original portfolio write-up; 85.63% and 73.17% ResNet50 validation remain unreconciled. The inspected Kaggle notebook version 1 has 17 cells and no saved outputs. There is no available complete confusion matrix, patient image, radiometric scale, exported activation map or verified test accuracy. The heat field and classifier are labelled schematic. The code uses a fixed XGBoost configuration, not an executed five-fold search.

Tracking's analysis source is pinned to `596501b7fcda1c082bf1a0e0bff181c9ea7b9cb0`; Metrica sample source is `e706dd506b360d69d9d123d5b8026e7294b13996`. Eight derived coordinate snapshots and 257 metric rows describe 298.88–310.12 seconds. The Home CSV hash was verified against the project summary, and endpoints were replayed from coordinates. Player11 is excluded as the Home goalkeeper. Missing ball values leave a 1.04-second gap; no interpolation is represented as observation. The recovery at 308.96 belongs to Away. Marker morphs explain snapshot differences; they are not a continuous tracking replay. Original raw CSVs are not distributed in the site.

BADI's ML source is pinned to `9e0c419259badb07f1bb5d36f43e88f54ac9d834`; Flask to `863c1c3cd491cb0a187df054a64a7804f645f498`. A 334-row monthly example contributes only its last 36 values. The code uses a 12-observation input and 12 monthly rollout steps; the legacy day-based description is not relabelled as verified source behavior. Bakery item counts and 852 Coffee/Bread co-occurrences among 9,465 baskets are direct aggregations. They are not customer revenue, model forecasts or causal findings. The inspected Flask handler returns original records instead of its forecast dataframe; this boundary remains visible. There is no verified deployment, adoption or accuracy claim.

To update evidence, pin the new source, reproduce the exported observations, update the dataset and explanatory text together, and rerun source-specific tests. Never resolve a source discrepancy by silently selecting the more attractive figure.
